## Context

See `proposal.md` - Why for motivation. Key hardware constraints that shape this design:

- Arduino Nano (ATmega328), fixed pinout: D2 (ECU PWM target, no free interrupt-safe pin to spare), D5/D6 (BTS7960 R_PWM/L_PWM), D7 (BTS7960 R_EN + L_EN tied together), D9 (MOSFET enabling A0), A0 (position potentiometer, shared wire with the motor), A1/A2 (BTS7960 R_IS/L_IS current sense), A3 (car battery voltage).
- Only 3 physical wires run to the position potentiometer/motor assembly; one wire is time-multiplexed between "motor power" and "position signal to A0" via a MOSFET gated by D9. D7 and D9 must never be enabled together (see `specs/exhaust-valve/actuator-interlock`).
- The potentiometer measured 0.455V at the closed stop and 2.619V at the open stop on this unit, i.e. roughly ADC counts 93-536 at the default 5V AREF (~443 counts of range) - comfortably above the 100-count minimum-range threshold, but the firmware must not assume this holds for every unit or after wear, hence the runtime mode selection in homing-calibration.
- The BTS7960 current-sense outputs (A1/A2) follow a linear scale of 0.00V = 0A to 4.0V = 3.4A (~0.85A per volt, i.e. ~3.4A per 818 ADC counts at the default 5V AREF). Current-related constants (stall thresholds, holding-current threshold) are expressed in Amps and converted to raw ADC counts through this single scale, so they stay meaningful/readable during bench calibration instead of being tuned as opaque ADC numbers.
- The valve has no return spring at either end of travel: nothing but the motor holds it against a mechanical stop.
- `platformio.ini` already declares `paulstoffregen/TimerOne`; `phatpaul/arduino-pwm-frequency-library` is removed (default Nano PWM frequency on D5/D6 is used, no need to raise it).
- `src/pwm_reader.cpp` already contains a working interrupt+micros()-based multi-pin PWM reader with a Timer1 watchdog for timeout detection - this is the starting point for the D2 reader, simplified to one pin.

## Goals / Non-Goals

**Goals:**
- Define the runtime task/state structure so the specs' requirements (interlock, homing, control modes, holding, fail-safe, logging) compose into one coherent, non-blocking main loop.
- Give concrete default values for every timing/threshold constant so implementation can start immediately, while keeping them as named, easily-tunable constants (per the user's request) since they must be re-calibrated on the bench/vehicle.
- Keep the control loop entirely non-blocking (no `delay()` in the hot path) so logging and the D2 interrupt reader are never starved.

**Non-Goals:**
- Tuning final PID gains, current thresholds, or timing constants to real hardware - that happens on the bench after this firmware exists (all such values are placeholders/starting points, listed in Decisions below).
- Adding an external command interface (e.g., serial commands to force re-homing or change mode) - not requested; can be a follow-up change.
- Compensating motor drive duty for battery voltage sag using A3 - A3 is logged only in this change.

## Decisions

### 1. Single time-multiplexed control loop, no RTOS/scheduler library
The whole firmware runs as one `millis()`-driven state machine in `loop()`, moving through `HOMING -> RUNNING -> (FAULT -> HOMING)` and, orthogonally, through the interlock's `DRIVE <-> READ` sub-cycle. A library-based scheduler was considered and rejected: the number of concurrent activities is small (PWM capture ISR, one control state machine, one logger), and an explicit state machine makes the D7/D9 mutual-exclusion invariant easy to audit in one place, which matters more here than scheduling convenience.

### 2. D2 capture stays interrupt-driven, adapted from `src/pwm_reader.cpp`
Reuse the existing CHANGE-interrupt + `micros()` technique, trimmed to a single pin, with the existing Timer1-driven periodic check repurposed as the signal-loss watchdog. Rejected alternative: `pulseIn()` (the original `src/main.cpp` approach) - it blocks for up to its timeout, which would stall the interlock/control timing and directly violates "read PWM without blocking."

### 3. Interlock burst cycle shape
```
|----- T_DRIVE_MS -----|-BTS7960 off-|--read--|-MOSFET off-|----- next drive -----|
 D7=HIGH                D7=LOW         D9=HIGH   D9=LOW        D7=HIGH
 (PID/holding duty       (motor          (A0        (motor
  applied)                coasting)      sampled)    still off)
```
One full cycle is one control tick (drive burst + 2x settle + read). Current (A1/A2) is sampled continuously during the drive burst, not just at the edges, since it doesn't share the interlocked wire.

- `T_DRIVE_MS = 20`: long enough to move the valve measurably per tick, short enough to keep the control loop responsive (~40Hz at these defaults). Placeholder, tune on bench.
- The dead-time is **not** a single constant: two different components turn off, so two different waits, both applied unconditionally on every transition (never skipped based on the code's own tracked state - see the correctness fix below):
  - `T_BTS7960_TURNOFF_MS = 2`: time to let the BTS7960's own R_PWM/L_PWM outputs actually finish turning off, before D9 enables (motor -> read) and before a reversed direction is applied. Per the user's reading of the BTS7960 datasheet, 2ms is a comfortable margin over its turn-off delay.
  - `T_READ_MOSFET_TURNOFF_US = 20` (microseconds, not milliseconds): time to let the D9 read-enable MOSFET, a 2N7000, actually finish turning off before the motor re-energizes (read -> motor). The 2N7000 datasheet gives a typical switching time of ~10ns; 20us is ~2000x that for margin, since the datasheet figure is the bare transistor under specific test conditions, not necessarily identical to being driven directly off an Arduino pin with no dedicated gate driver. Implemented with `delayMicroseconds()` rather than `delay()`, since it's three orders of magnitude smaller than `T_BTS7960_TURNOFF_MS`.

  These were originally a single `T_SETTLE_MS` reused everywhere; splitting them doesn't change any spec requirement (each interlock scenario already says "the configured settle time" independently for its own transition), it just lets each be tuned to the component that actually governs it.

  **Correctness fix during implementation**: `ActuatorInterlock::readPositionRaw()` originally only disabled the motor and waited if its own `s_motorEnabled` bookkeeping said the motor was on - but `HomingCalibration` calls `stopMotor()` (which clears that flag) immediately before `readPositionRaw()`, so the wait was silently skipped on that path. Fixed by making `readPositionRaw()` always disable the motor outputs and wait, unconditionally, regardless of tracked state - the hardware guarantee must not depend on software bookkeeping being right.
- `ADC_PRESCALER = 32` (500kHz ADC clock, ~26-28us conversion vs. ~104us at the default prescaler 128): justified by the measured 443-count sensor range being well above the 100-count mode-selection threshold, so the reduced accuracy at this prescaler is acceptable. Alternative considered: prescaler 128 (Arduino default, full accuracy) - rejected as unnecessarily slow given the requirement to read "as fast as possible" and the available margin.

### 4. Control mode is a runtime flag set once per homing cycle
`ControlMode { POSITION, TIME }`, selected in homing-calibration and re-evaluated every time homing re-runs (including after a mid-travel fault). Both modes share the same interlock burst cycle and the same holding-at-stops logic; they differ only in how "current position" is obtained (sensor reading vs. dead-reckoning accumulator).

### 5. Dead-reckoning accumulator for TIME mode
Position estimate is a float in [0.0, 1.0] (closed to open). Each drive burst adds or subtracts `T_DRIVE_MS / t_open_ms` or `T_DRIVE_MS / t_close_ms` depending on the active direction, clamped to [0, 1]. No special case is needed for direction reversal mid-travel - the correct per-direction speed constant is just picked each tick based on the currently commanded direction. Current-based stop detection still fires in this mode and resyncs the estimate to 0.0 or 1.0 whenever a stop is actually reached, bounding drift.

### 6. Holding-at-stops: continuous reduced duty, not pulsed
When the target is an extreme and the valve is confirmed there (by sensor deadband in POSITION mode, or by current-based stop confirmation in TIME mode), the drive burst applies a fixed `HOLD_DUTY_PERCENT` (well below normal driving duty) toward that stop every cycle, instead of a PID-computed duty or a fully-off motor. Alternative considered: pulsed hold (short on / long off) - rejected for now as unnecessary added complexity; continuous low duty is simpler to reason about and the holding-current protection (Decision 7) already provides a thermal safety net. This can be revisited if bench testing shows it runs hot.

This same mechanism implements the D2 signal-loss fail-safe: losing the signal simply forces `target = fully open`, which drives the existing "reach and hold" path already used for a normal fully-open command - no separate fail-safe code path is needed.

### 7. Holding-current protection as a graduated response, not a hard fault
While holding, if the holding-direction current-sense reading exceeds `HOLD_CURRENT_THRESHOLD` for more than `HOLD_CURRENT_DURATION_MS`, the firmware halves (or otherwise reduces by a configured step) `HOLD_DUTY_PERCENT` for that episode and logs a fault event, rather than cutting the motor entirely or re-homing. Rationale: at an intentional stop, backing off force is safe (the mechanical stop is still doing its job); a full cutoff would defeat the no-spring fail-safe guarantee, and re-homing would be disruptive for what may just be a temporarily stiff spot.

### 8. Mid-travel overcurrent vs. stop confirmation share one threshold family, different context
`STALL_CURRENT_THRESHOLD_R_AMPS` / `STALL_CURRENT_THRESHOLD_L_AMPS` (per direction, since spring/gravity/exhaust-pressure assist can differ by direction) are used both by homing-calibration (to detect the physical stop while sweeping) and by valve-position-control (to detect an unexpected mid-travel obstruction). The distinguishing factor is the current position/estimate relative to the recorded stops (within deadband of a stop = expected; elsewhere = fault), not a different current value - keeping one threshold per direction avoids maintaining two calibrations that must stay consistent with each other. `HOLD_CURRENT_THRESHOLD_AMPS` (Decision 7) is a separate, typically lower, constant on the same Amps scale, since holding current at rest is expected to be much lower than the current drawn while actively driving into a stop.

All three are stored/configured in Amps and converted once, via the 0V=0A/4.0V=3.4A scale, into the raw ADC-count comparison actually used at runtime.

### 9. Centralized tunable-constants header
All constants named above and in the specs live in a single `include/config.h` (or equivalent), grouped by concern (timing, ADC, current thresholds, PID gains, deadbands, holding, logging intervals), each with a brief comment on what it affects and a placeholder/starting-point value. No magic numbers in the logic files. This directly satisfies the user's requirement to be able to populate calibration values later without hunting through the codebase.

### 10. Unconditional pre-sweep release kick before homing
Bench testing found that when the valve is already resting at the closed stop when homing starts, `driveToStop(Closing)` stalls on its very first current sample - `closeTimeMs` comes back at ~0ms, which then corrupts the TIME-mode dead-reckoning speed (`T_DRIVE_MS / closeTimeMs`) for the whole session. Fix: before the close-then-open sweep, unconditionally drive Opening at a fixed high duty (`HOMING_PRE_OPEN_KICK_DUTY_PERCENT`, 100%) for a fixed short duration (`HOMING_PRE_OPEN_KICK_MS`, 100ms), with no stall-current check during the kick itself, then proceed with the sweep exactly as before. Two new named constants in `include/config.h`, per Decision 9.

Rejected alternative: only run the kick conditionally (detect "already at closed stop" first via current sensing, skip otherwise). Rejected for simplicity - an unconditional fixed-duration kick needs no extra state or pre-check logic, costs a constant, negligible 100ms on every homing run, and behaves identically whether or not the valve happened to be at the closed stop.

This only guarantees `closeTimeMs` is never pathologically ~0; it does not make either leg's timing a guaranteed true full-stroke measurement when homing starts from an arbitrary mid-travel position (closeTimeMs still measures "wherever homing started, plus the kick" to closed) - out of scope for this fix, which targets the observed already-closed failure mode specifically.

**[Risk]** The kick has no stall-current check, so if the valve happens to already be at the *open* stop when homing starts, it drives into that stop at 100% duty for the full 100ms with no early cutoff. → **Mitigation**: bounded to 100ms (same order of magnitude as one normal drive tick), and no worse than the dwell the valve already tolerates while `driveToStop(Opening)` polls for stall current during a normal sweep.

### 11. Dynamic, baseline-relative stall detection for homing (replaces the fixed threshold in `driveToStop()` only)
Bench disassembly found the throttle body has a small mechanical detent partway through travel that briefly bumps drive current as the valve passes it. A fixed absolute `STALL_CURRENT_THRESHOLD_R/L_AMPS` value can't reliably tell that bump apart from the genuine end-of-travel stall - set low enough to catch a light stall and the detent trips it early; set high enough to clear the detent and a unit with lower stall current might never trip it. Scoped to homing's `driveToStop()` only, per explicit decision - `valve-position-control`'s mid-travel overcurrent fault and holding-current protection (Decision 8) keep the existing fixed-threshold approach unchanged, since that path must react correctly to a genuine obstruction during normal operation independent of any per-run baseline, and bench testing did not show a problem there.

`driveToStop()` now tracks a running baseline of the active direction's current via an exponential moving average (`HOMING_CURRENT_BASELINE_EMA_ALPHA`), seeded after a short inrush-ignore window (`HOMING_CURRENT_INRUSH_IGNORE_MS`) at the start of each drive so motor start-up inrush isn't mistaken for the baseline. A reading at or above `baseline * HOMING_CURRENT_SPIKE_FACTOR + HOMING_CURRENT_SPIKE_MARGIN_AMPS` is a candidate stall; it must stay at or above that line for `HOMING_CURRENT_SPIKE_SUSTAIN_MS` to be confirmed - the sustain window is what actually separates the detent's brief bump (current subsides as the valve keeps moving through it) from a true stall (current stays elevated because the motor has stopped moving). Independently of all of this, `HOMING_CURRENT_HARD_LIMIT_AMPS` is an absolute ceiling that stops the drive immediately if ever reached, as a backstop in case the dynamic logic fails to trigger for any reason; `HOMING_MAX_DRIVE_MS`'s time-based backstop is unchanged. Six new named constants in `include/config.h`, per Decision 9. `STALL_CURRENT_THRESHOLD_R/L_AMPS` are untouched.

Rejected alternative: apply the same dynamic detection to the mid-travel fault/holding checks too, unifying all current-based checks on one mechanism. Rejected (for now) as a larger, riskier change than what bench testing actually showed a problem with.

**[Risk]** If `driveToStop()` somehow starts while the valve is already stalled in that direction (not the closed-stop-at-boot case, which the pre-sweep kick (Decision 10) already handles), the first accepted sample seeds the baseline from the already-stalled current itself, and no further rise would look "discrepant" - detection would fall through to the time-based `HOMING_MAX_DRIVE_MS` backstop instead of the current-based one. → **Mitigation**: `HOMING_CURRENT_HARD_LIMIT_AMPS` still catches a hard stall outright, and this scenario shouldn't arise in the normal homing flow, since the pre-sweep kick guarantees the closing leg doesn't start already at the closed stop, and the opening leg always starts exactly at the closed stop it just reached (i.e., moving away from a stop, not into one).

**[Risk]** A relative/baseline approach can still under- or over-trigger if the true stall current ends up close to the previous baseline (e.g. a lightly spring/pressure-assisted direction) - the multiplicative factor may not produce enough separation. → **Mitigation**: `HOMING_CURRENT_SPIKE_FACTOR`, `_MARGIN_AMPS`, and `_SUSTAIN_MS` are exposed as bench-tunable constants precisely to be calibrated per-unit, and the absolute hard limit remains as a final backstop regardless of how they're tuned.

### 12. Block-average the raw current signal before Decision 11's baseline/spike comparison
First bench run of Decision 11 failed: the closing leg timed out at `HOMING_MAX_DRIVE_MS` without ever detecting the stop. The serial log showed why - a single raw `analogRead` of R_IS/L_IS alternates between roughly the PWM "on" current (~2A) and the decaying "off" current (~0.5A) depending purely on when, within the ~980Hz PWM period (D5/D6's default Nano PWM frequency), the ADC happened to sample. The baseline EMA correctly averaged this down to the true running current (~1.6A), but comparing a single noisy raw sample (peaking around 2.2A) against `baseline * SPIKE_FACTOR + MARGIN` (≈3.2A) meant the ripple's own peaks never got close to the spike line - the dynamic check was structurally unable to fire, independent of how the constants were tuned.

Fix: raw samples are now block-averaged over `HOMING_CURRENT_FILTER_WINDOW_MS` (a handful of PWM periods) before being fed to the baseline/spike logic from Decision 11, which is otherwise unchanged. `HOMING_CURRENT_HARD_LIMIT_AMPS` still checks the raw, unfiltered reading every iteration, since that backstop must react immediately and not wait for a window to close.

Same bench run also showed the Opening leg hit the hard current limit almost immediately, then the very next mid-travel check in `valve-position-control` faulted again at a similarly high current - consistent with the valve still resting at (or immediately adjacent to) the closed stop for the entire failed closing attempt, i.e. it may never have needed the stall detection to fire at all during that run. Also, per this same run's log, `HOMING_DRIVE_DUTY_PERCENT` was tied to `MOTOR_DRIVE_DUTY_PERCENT` (40%) at the time - decoupled into its own, higher placeholder (70%) alongside this fix, on the hypothesis that a bigger running-vs-stalled current gap at higher duty will make the dynamic detection's job easier; this is unverified and should be checked on the next bench run along with the filtering fix itself.

### 13. Baseline is learned once and frozen, not continuously updated via EMA
Second bench run (with Decision 12's filtering in place) failed differently: the closing leg still timed out, and the printed `filtered`/`baseline` pairs showed the EMA baseline climbing from ~0.15A to ~0.65A during the motor's initial ramp-up (a real mechanical breakaway/spin-up transient, not electrical inrush - current was still rising ~600-700ms in), then staying pinned at ~0.65A for the rest of the 5s drive even though the filtered current had already settled to a visibly lower, stable ~0.35-0.41A. An EMA that only updates on non-spike samples is a feedback loop between the value it's tracking and the threshold gating its own updates; exactly how it got and stayed stuck above the true running current wasn't fully reproducible by hand-tracing the log alone, which is itself the problem - a stall-detection mechanism whose steady-state behavior can't be confidently predicted from its own inputs is too fragile for a bench-iteration loop this slow (each attempt costs a full flash-and-run cycle).

Replaced with a simpler, non-feedback design: `HOMING_CURRENT_INRUSH_IGNORE_MS` (raised to 700ms - long enough to cover the observed mechanical ramp-up, not just electrical inrush) is skipped entirely, then the next `HOMING_CURRENT_BASELINE_LEARN_MS` (300ms) of filtered samples are averaged into a single baseline value, which is logged once (`Logger::event`) and held fixed for the rest of that leg - no further updates. `HOMING_CURRENT_BASELINE_EMA_ALPHA` is removed; `SPIKE_FACTOR`/`_MARGIN_AMPS`/`_SUSTAIN_MS`/`HARD_LIMIT_AMPS` are unchanged. Logging the locked baseline and its resulting threshold as an event (not just the throttled per-window Serial print) means the next bench log states outright what number the sweep is comparing against, instead of needing to be inferred from a moving series of prints.

**[Risk]** If the learn window (`INRUSH_IGNORE_MS` + `BASELINE_LEARN_MS` = 1000ms total) still lands partway through the mechanical ramp-up on a different unit or duty setting, the locked baseline will be too high, same failure mode as before just capped rather than unbounded. → **Mitigation**: both durations are bench-tunable, and the newly-logged "baseline locked at X" event makes it immediately visible on the next run whether that happened, rather than needing to be inferred from a raw print series.

### 14. Absolute floor under the spike threshold, and an open question about whether travel is fast enough to break the whole baseline premise
Third bench run (with Decision 13's frozen-baseline in place) surfaced a distinct bug: the Closing leg's baseline locked at 0.00A (a direction that, per the log, drew almost no current for the first ~2.6s), making its spike threshold collapse to just `SPIKE_MARGIN_AMPS` (0.3A) - a completely ordinary current uptick (0.61A) crossed that trivial bar, with no way to tell whether it reflected a genuine stall. Fix: `HOMING_CURRENT_SPIKE_MIN_ABS_AMPS` (1.0A) is now a hard floor under the computed threshold (`max(baseline * FACTOR + MARGIN, MIN_ABS_AMPS)`), so a near-zero learned baseline can no longer produce a trivially-crossed threshold.

That same run also raised a bigger open question, unresolved as of this decision: both legs' current plateaued essentially flat for the *entire* remaining multi-second window immediately after their baseline locked (Closing at 1.48A, Opening at 1.86A, in the same run's second homing attempt), suggesting the valve may already have been resting at or near a stop *before* the 1000ms learn window even completed - which would mean the learned "baseline" is actually already-stalled current, not free-running current, and no threshold built from it could ever detect a further rise. Combined with a *different* run's Closing leg locking baseline at 0.00A and only rising after ~2.6s of apparently genuine travel, the same direction is producing inconsistent baseline readings from run to run. This can't be resolved from serial logs alone - see the open question below about a bench observer physically watching the sweep.

### 15. Corrected assumption: no mid-travel detent, and the sweep is much faster than the baseline-learning window
Decision 14's open question is resolved by direct observation: watching the physical sweep confirms it runs stop-to-stop in well under 1 second. This also corrects the premise behind Decisions 11-14: what was originally described as a mechanical detent partway through travel (from feeling resistance while disassembling the motor) is a non-back-drivable mechanism that only prevents the butterfly being turned by hand - it has no effect on motor-driven current, so there was never a mid-travel current bump to distinguish from the real stop.

The actual constraint was always timing: `HOMING_CURRENT_INRUSH_IGNORE_MS` + `HOMING_CURRENT_BASELINE_LEARN_MS` totaled 1000ms - longer than the entire sweep - so the "learned baseline" was, in every run, already-stalled current rather than free-running current, exactly matching Decision 14's flat-plateau observation. Both are cut down to fit inside a sub-second sweep: `HOMING_CURRENT_INRUSH_IGNORE_MS` (5ms) only needs to clear the ~2ms BTS7960 direction-reversal dead-time, and `HOMING_CURRENT_BASELINE_LEARN_MS` (50ms) is the window immediately after that. `HOMING_MAX_DRIVE_MS` is cut from 5000ms to 1500ms to match, and `HOMING_CURRENT_SPIKE_SUSTAIN_MS` from 40ms to 15ms, since there's no detent bump to debounce against anymore - it now only needs to reject a single noisy sample.

The homing-calibration spec's "detent" scenario is reworded to "brief current glitch" to match this corrected understanding - the sustained-duration debounce is still worth keeping as general noise immunity, just not for the reason originally given.

**[Risk]** If the 50ms learn window still doesn't fully clear before the valve reaches a stop on a given run (i.e. the sweep is faster than even this), the same already-stalled-baseline failure mode recurs, just with a smaller window. → **Mitigation**: the locked-baseline event log (Decision 13) makes this immediately visible on the next run - a baseline that lands close to the direction's known stall-current range, rather than a lower free-running range, is the signal to shrink the window further.

### 16. Continuous holding replaced by a one-shot seating push (supersedes Decisions 6-7)
The actuator's drive mechanism is non-back-drivable (Decision 15) - it can't be turned by an external force once the motor stops driving it. Decisions 6-7's continuous holding force (a low duty applied indefinitely against a confirmed stop, with graduated current-based backoff) was built on the assumption that something needed to keep pushing against the stop the whole time to counteract the lack of a return spring; that assumption no longer holds once the mechanism itself is known to stay put unpowered.

Replaced with a one-shot push: the moment the valve is first confirmed at a stop matching the current target, it drives at `SEAT_KICK_DUTY_PERCENT` for `SEAT_KICK_MS`, then releases the motor entirely - not "reach and coast," but a firm, bounded push to seat it fully against the mechanical stop rather than just within the position deadband. It does not repeat while the valve stays confirmed there and the target doesn't change. `HOLD_DUTY_PERCENT`, `HOLD_CURRENT_THRESHOLD_AMPS`, `HOLD_CURRENT_DURATION_MS`, and `HOLD_CURRENT_BACKOFF_FACTOR` are removed along with the graduated backoff response they supported (Decision 7) - a bounded single pulse has no ongoing thermal exposure to protect against.

The D2 signal-loss fail-safe (still forcing `target = fully open`) is unchanged in structure: it reuses this same seating-push path, now released afterward instead of held.

### 17. Centralize current-sense averaging in `CurrentSensing`, remove duplicate windowing in homing
Bench feedback from normal (non-homing) operation showed `valve-position-control`'s mid-travel overcurrent check (task 6.5) suffers the same PWM-ripple problem Decision 12 fixed for homing: a single raw `analogRead()` of R_IS/L_IS alternates between the PWM "on" and "off" current depending on sample timing, so comparing a raw sample against a fixed threshold is unreliable outside of homing too. Rather than duplicating Decision 12's block-averaging in a second place, the averaging moves into `CurrentSensing::readRAmps()`/`readLAmps()` (and therefore `readActiveDirectionAmps()`) themselves, so every caller gets a filtered reading with no caller-side filtering logic of its own.

Both functions take a `windowMs` parameter instead of a single implicit window, since the two use sites need different tradeoffs between noise immunity and iteration granularity:
- Callers outside of homing's sweep (mid-travel fault, telemetry) use `CURRENT_SENSE_FILTER_WINDOW_MS` (5ms - the same "handful of PWM periods" value Decision 12 already validated on this hardware, moved out of the `HOMING_` naming since it's no longer homing-specific). Each of these callers takes exactly one reading per call, so a 5ms block is a one-off cost, not a per-iteration one.
- `HomingCalibration::driveToStop()` uses the shorter `CURRENT_SENSE_HARD_LIMIT_WINDOW_MS` (1ms placeholder - approximately one PWM period) for *every* reading inside its polling loop, including the ones feeding baseline-learning and spike detection, not just the `HOMING_CURRENT_HARD_LIMIT_AMPS` check. Taking two differently-windowed readings per loop iteration (a fast one for the hard limit, a 5ms one for baseline/spike) was tried and rejected: each iteration would cost ~6ms, coarser than `HOMING_CURRENT_INRUSH_IGNORE_MS` (3ms), which would then be skipped on the very first iteration regardless of its configured value. A single 1ms window keeps iteration cost low enough for `HOMING_CURRENT_INRUSH_IGNORE_MS` to still mean something, at the cost of the baseline/spike math seeing a noisier (1-period, not 5-period) average than Decision 12 validated.

`HomingCalibration::driveToStop()`'s own `windowSum`/`windowCount`/`windowStartMs` block-averaging loop is removed - it duplicated the same fix Decision 12 already made, now redundant once `CurrentSensing` filters at the source. `driveToStop()` keeps only what's unique to homing: the inrush-ignore window, one-shot baseline learning, and spike-sustain confirmation, all now operating directly on `CurrentSensing`'s already-filtered output.

**[Risk]** Both `readRAmps`/`readLAmps` calls now block for their `windowMs` duration instead of returning immediately - `ValvePositionControl::monitorDrivingPhase()` (called once per pass through `loop()` during a drive burst) now costs up to 5ms per call instead of one ADC conversion (~28us). → **Mitigation**: the same order of magnitude as blocking already tolerated elsewhere in this design (e.g. `T_BTS7960_TURNOFF_MS = 2ms` via `delay()` in `ActuatorInterlock::drive()`), and well within `T_DRIVE_MS = 20ms` per burst; nothing in the hot path needs sub-millisecond polling (D2 capture is interrupt-driven, `Logger::telemetry` throttles internally).

**[Risk]** `CURRENT_SENSE_HARD_LIMIT_WINDOW_MS` (1ms placeholder) is a bench-tunable guess at "long enough to average a real PWM cycle, short enough to still act as a fast backstop" - untested on hardware. → **Mitigation**: exposed as its own named constant in `include/config.h`, independent of the normal filter window, so it can be retuned without affecting the rest of current-sensing behavior.

**[Risk]** Homing's baseline/spike detection now averages over only ~1 PWM period per reading instead of the ~5 periods Decision 12 validated, since it shares `CURRENT_SENSE_HARD_LIMIT_WINDOW_MS` with the hard-limit check. → **Mitigation**: still an order of magnitude better than the single-instant raw sample Decision 12's bug report described; if bench testing shows the baseline/spike math is still too noisy at 1ms, the fix is a targeted one (e.g. average a handful of `CURRENT_SENSE_HARD_LIMIT_WINDOW_MS` readings before feeding them to baseline/spike, without reintroducing a second full-length blocking read per iteration), not a reversion to this decision.

### 18. Bench-tuned percentage compensation for a consistent gap between `driveToStop()`'s measured stop time and the valve's real physical stop

Bench feedback from TIME-mode operation found the dead-reckoning estimate lagging the valve's real position by a large, fairly reproducible margin at both extremes: driving toward open, the valve was already physically at its stop while the estimate (and the ECU target driving it) still read ~60-70%; driving toward closed, the valve was already physically closed at ~29-40%. Since `DeadReckoningEstimator::update()` accumulates `elapsedMs / openTimeMs` (or `closeTimeMs`) per tick using exactly the times `driveToStop()` measured, a lag at both ends this large and this consistent means `closeTimeMs`/`openTimeMs` are themselves larger than the valve's true full-stroke time - not sensor noise or a bug in the accumulation math.

Investigated and ruled out with bench evidence before treating this as unfixable in software:
- **`HOMING_CURRENT_SPIKE_SUSTAIN_MS`'s confirmation wait** inflating the reported time: real (a few ms, now excluded - see `driveToStop()`'s use of `spikeStartMs` instead of the confirmation instant), but far too small to account for the observed gap.
- **Baseline learned during motor ramp-up**, inflating `spikeThreshold` (the same failure mode as Decisions 13/14): checked against actual bench logs - `HOMING_CURRENT_SPIKE_MIN_ABS_AMPS`'s floor dominates the computed threshold in the observed runs regardless of the learned baseline, so this isn't currently biasing detection.
- **1ms block-average window aliasing against the ~1ms PWM period**, defeating `HOMING_CURRENT_SPIKE_SUSTAIN_MS` with frequent near-miss resets: measured directly (`spikeResetCount`/`spikeMaxStreakMs` counters added temporarily to `driveToStop()`) - only a handful of resets with short streaks, not the systematic pattern this hypothesis predicts.
- **`DeadReckoningEstimator`'s own math**: cross-checked telemetry (`[TEL] pos=`) against the logged `closeTimeMs`/`openTimeMs` across several ticks - the accumulation matches the configured time exactly, so the estimator is faithfully reproducing whatever time it's given.

With the software-side explanations checked and ruled out, the working theory is mechanical: slack between the motor and the valve (gearbox backlash or a non-rigid coupling) lets the valve reach its physical stop before the motor shaft is actually prevented from turning, so the current spike `driveToStop()` waits for arrives later than the real stop. Current-based detection has no way to see this, since the current only reflects what's happening at the motor shaft, not the valve plate.

Fix: `HOMING_CLOSE_TIME_COMPENSATION_PERCENT`/`HOMING_OPEN_TIME_COMPENSATION_PERCENT` (config.h) scale `closeTimeMs`/`openTimeMs` down by a bench-tuned percentage in `HomingCalibration::run()`, right after `driveToStop()` returns - `driveToStop()` itself keeps reporting the raw current-detected time (still logged, alongside the compensated value, in the `homing: done` event) so future bench tuning can see both. Separate constants per direction, since the observed gap wasn't symmetric (~34% opening, ~29% closing in the bench run that prompted this). Started at a conservative 15% both directions rather than the full observed gap, pending further bench validation of how consistent the gap is across runs/temperature/wear.

**[Risk]** This compensates the symptom, not the mechanical cause - if the underlying slack changes (wear, a different unit, temperature), the compensation percentage will drift out of calibration the same way any bench-tuned constant would. → **Mitigation**: exposed as named, per-direction, bench-tunable constants like everything else in `config.h`; the raw (uncompensated) time is still logged for comparison on every homing run, making drift visible without needing to touch code.

**[Risk]** The mechanical-slack theory is the leading hypothesis, not confirmed by direct physical inspection (e.g. feeling for backlash with the motor de-energized, or comparing on video when the valve visually stops against when the motor's load sound changes). → **Mitigation**: none needed for the compensation itself to work as a bench-tuned correction; physical confirmation would only matter if the compensation stops tracking the real gap well.

## Risks / Trade-offs

- **[Risk]** Fixed-length drive bursts mean the motor never spins continuously; it always starts/stops every cycle, which is rougher on the motor/gearbox and draws more inrush current per burst than smooth continuous drive. → **Mitigation**: this is an inherent consequence of the 3-wire shared design, not something software can avoid; `T_DRIVE_MS` is tunable to trade responsiveness against how "steppy" the motion feels.
- **[Risk]** Lower ADC prescaler (32) trades reading accuracy for speed. → **Mitigation**: the measured 443-count sensor range leaves ~4x headroom over the 100-count mode-selection threshold; if a future unit has a narrower sensor range, `ADC_PRESCALER` can be raised back toward 128 at the cost of read-window duration.
- **[Risk]** The seating push (Decision 16) drives at `SEAT_KICK_DUTY_PERCENT` for `SEAT_KICK_MS` with no current-based fault check, since it's a bounded, one-shot action into a position already confirmed as a stop. → **Mitigation**: both are exposed as bench-tunable constants, and the bound itself (a single 100ms pulse, not indefinite force) limits the exposure compared to the continuous holding this replaced.
- **[Risk]** Re-homing after a mid-travel fault temporarily loses tracking of the ECU's requested target while the sweep runs. → **Mitigation**: this is accepted as the safer alternative to resuming control with unknown/unverified stop positions; the fail-safe-to-open behavior does not apply here since D2 itself is still valid - the valve simply re-syncs before resuming.
- **[Trade-off]** One combined interlock burst cycle for both current-sensing-only stall checks (which don't need the mutex) and A0 position reads (which do) means position-mode control ticks at the same rate as the interlock cycle even though current sensing alone could run faster. Accepted for simplicity; the two are kept on the same cadence rather than introducing a second, faster loop.

## Migration Plan

This is a new (previously non-existent) firmware capability set on a project that had only bench-test sketches, so there is no in-place migration of running behavior:

1. Remove `src/main.cpp`, `src/leitor_pwm.cpp`, and the `arduino-pwm-frequency-library` entry in `platformio.ini` (tasks.md covers the exact steps).
2. Add the new `include/config.h` constants header, the interlock/homing/control/logging modules, and the trimmed single-pin version of `src/pwm_reader.cpp`'s technique.
3. Flash and bench-test with the valve disconnected from the exhaust (motor/pot only) to calibrate `T_DRIVE_MS`, `T_BTS7960_TURNOFF_MS`, `T_READ_MOSFET_TURNOFF_US`, stall-current thresholds, PID gains, and holding duty before any vehicle installation.
4. No rollback concerns beyond re-flashing the previous bench-test sketch if needed; nothing here is persisted to EEPROM/flash (all calibration is RAM-only, re-derived every power-on by design).

## Open Questions

- Exact `HOLD_DUTY_PERCENT` step-down factor and `HOLD_CURRENT_DURATION_MS` when the holding-current protection trips (Decision 7) are left as tunable constants with placeholder values - resolving them requires bench measurement of actual holding current at the mechanical stops, which cannot be done before hardware is in hand.
- Whether `T_DRIVE_MS = 20` gives visually smooth-enough motion or should be shortened/lengthened is likewise a bench-tuning question, not an architectural one - changing it later does not affect any spec or the task breakdown.
- Resolved by Decision 15: the sweep runs in well under 1 second, so `HOMING_CURRENT_INRUSH_IGNORE_MS`/`HOMING_CURRENT_BASELINE_LEARN_MS` are cut down to fit inside it. Whether 5ms/50ms is itself short enough, or needs to shrink further, is still a bench-tuning question, not an architectural one - the locked-baseline event log makes that directly observable on the next run.
